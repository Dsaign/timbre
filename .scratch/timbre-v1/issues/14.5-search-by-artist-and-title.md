# 14.5: Search by artist and song title

**What to build:** a visitor who types an artist or a song title gets that artist's or song's Songs first, then Songs that sound like them. Today "Linkin Park" finds nothing: a Song's profile text (the text its vector is built from) holds moods, instruments and tags, never its title or artist, so the model can't connect a name to a Song.

**Blocked by:** 14

**Status:** ready-for-agent

## Decisions (owner, 2026-11-16)

- **Order:** name matches first, ordered by Popularity, then the usual Fit-based Matches without repeats. "Linkin Park" shows Linkin Park Songs, then similar nu metal and rap rock.
- **Related Songs:** found by similarity to the matched Songs (the average of their vectors), not by searching the typed text, which the model can't read as a name.
- **Matching:** ignores case, accents and small typos ("linkin park", "Beyonce", "linkn park"), using Postgres `pg_trgm` (ships with Postgres; one migration, no new dependency).
- **Out of scope:** Descriptions that mix a name and a feel ("Linkin Park mais calmo", "algo tipo Radiohead com piano"). These still run through Fit-based search as today. Possible later ticket.

## Acceptance criteria

- [ ] A migration enables `pg_trgm` and adds trigram indexes on `catalog.songs` title and artist (plain SQL dbmate, bound parameters only).
- [ ] When the Description matches an artist or title above a similarity threshold, Search returns those Songs first (by Popularity), then the Songs closest to the average vector of the matched Songs. No Song appears twice, and the total count and paging ("carregar mais") stay consistent across both parts.
- [ ] When nothing matches by name, Search behaves exactly as today. Feel Descriptions ("violão calmo para estudar") must not pick up accidental name matches. The threshold is chosen and checked against the sample Descriptions and the Benchmark Descriptions, with the rule written next to it.
- [ ] The nonsense string `xkqzv wplmr tjhgf` still gets 0 Matches.
- [ ] The API contract stays the same: same request and response shape, so `back/openapi.json` and `front/lib/api/schema.d.ts` don't change. If they must, regenerate both.
- [ ] Spec and glossary updated: `.scratch/timbre-v1/spec.md` (problem statement and a user story for searching by name) and `CONTEXT.md` (a Match can now come from a name match or from Fit above the cutoff).
- [ ] Tests (pytest in Compose): an exact artist, an artist with a typo and missing accent, a song title, a feel Description with no name match (unchanged results), paging across the name/related boundary, and the nonsense guard.
- [ ] The Benchmark and the evaluate job are unchanged: they score Descriptions → Fit, and name matching sits outside the model, so ticket 15's promote rule isn't affected.
