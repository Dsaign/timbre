# 20: Search quality before launch

**What to build:** search on the production Catalog (38,286 Songs) returns Matches that fit the Description, with no obvious intruders, before the project is announced. Three things hold it back today: Songs keep too few tags, a single-word tag barely counts in a long Description, and the Benchmark is too small to tell a better model from a worse one. This ticket fixes the tags, makes the tag weight ignore filler words, adds a large generated Benchmark with a precision metric, and picks the model version to promote from those numbers.

**Blocked by:** none

**Status:** ready-for-agent

## What the owner saw (production, 2026-11-18)

Production's promoted model is version 1 (plain e5, cutoff 0.83). Top 16 Matches:

- "Emo para chorar e cantar gritando": emo bands, but also "Wait for It" (Hamilton cast), Slayer "Bloodline", Meshuggah, Juice WRLD.
- "emo triste pra gritar junto no refrão": Kid Cudi, Moby, Gil Scott‑Heron, Air, Manu Chao.
- "emo dos anos 2000 com guitarra e gritos": Slayer, Moby, Rihanna "G4L", Tycho, Lily Allen, "Wait for It".

With the same 38k Catalog copied locally, the local promoted version 17 returns almost only emo bands for the first two queries (Brand New, Jimmy Eat World, Paramore, Panic!). Yet the Benchmark scores version 17 at 0.110 and plain e5 at 0.120. The Benchmark (105 Descriptions, 3 expected Songs each, recall in the top 24) cannot see the difference.

## Causes found

1. **Tags.** `metabrainz.top_tags` keeps only the most specific level that has any tag. A recording with one tag of its own drops its artist's tags: Slayer "Bloodline" has only `00s`, "Wait for It" has none. In production 4,813 Songs have 1–2 tags, 2,635 have 3, 3,466 have 4, and 10 have none (`TAGS_PER_SONG` is 5).
2. **Tag weight.** In `search.MATCHES_SQL` a tag's weight is the share of Description words it covers. Filler words count: "emo" covers 1/6 of "Emo para chorar e cantar gritando" and 1/8 of "emo dos anos 2000 com guitarra e gritos", so the tag ranking hardly counts.
3. **Benchmark.** Too few Descriptions and expected Songs, and recall alone never punishes an intruder in the first screen.

## Tasks

- [ ] `top_tags` fills up to `TAGS_PER_SONG` going down the levels (recording, then release_group, then artist), most specific first, without duplicates. Unit test with a recording that has one tag of its own.
- [ ] A retag job (a `jobs.queue` kind, like `import-catalog`) re-fetches tags for every Song with fewer than `TAGS_PER_SONG` tags, in `METADATA_BATCH` calls. It updates each Song in place, so the Song stays searchable during the run, and then queues `build-vectors` for the changed Songs. It reuses `tag_seed_songs`' pattern; generalize that function rather than copying it. Test it with mocked ListenBrainz responses.
- [ ] The tag weight's word count ignores filler words (Portuguese and English: articles, prepositions, conjunctions, "pra", "pro", "com", "dos", ...). Example: "Emo para chorar e cantar gritando" counts 4 words ("emo chorar cantar gritando"), so "emo" covers 1/4. The tag phrases themselves don't change. If this changes SQL functions, it is a dbmate migration. Tests in `tests/test_search.py`.
- [ ] **Generated Benchmark**, `back/src/timbre_back/benchmark_generated.json`, loaded by `benchmark.FILES`, with `"source": "generated"` and `"reviewed": false`. Generate as many Descriptions as the Catalog supports (aim for 1,000 or more) from what the Catalog holds: frequent tags (genres, scenes, decades) crossed with AcousticBrainz moods and voice labels. Each Description is phrased the way a visitor would type it, half in Brazilian Portuguese and half in English, with popular words: "emo pra chorar", "rock dos anos 80 pra dirigir", "sad indie with female vocals", "metal pesado pra treinar". Each entry has:
  - at least 3 expected Songs, picked from Songs that have the Description's tag among their 3 most-voted and fit its mood labels, preferring popular Songs;
  - `accept_tags`: the tag keys that make a Match relevant to the Description (for example `["emo", "screamo", "post hardcore", "pop punk"]`), used by the precision metric.
  - The generator is a committed script in `back/scripts/`, deterministic (fixed seed), and reads the local database. Commit its output. Song IDs are MusicBrainz recording IDs, the same in production. Tags themselves are not committed (ADR 0002): only tag keys as words in `accept_tags`.
  - So the Benchmark does not just test tag lookup, at least half the Descriptions must not contain any of their `accept_tags` word for word (paraphrases: "som pesado e agressivo" instead of "metal", Portuguese words for English tags).
- [ ] **precision@16**: the share of a Description's first 16 Matches (the first screen) whose Song has any of its `accept_tags` among its tags, averaged over the entries that have `accept_tags`. The evaluate job logs recall@24 and precision@16 separately per file (hand-written, drafted, generated) and records them on the model version (a migration adds the columns). Promotion keeps using today's score. The hand-written emo entry (already added, IDs filled) gets `accept_tags` too.
- [ ] Training exclusion: `train.may_train_on` keeps every Description within 0.92 of a Benchmark Description out of training. Report how many training Descriptions the generated set excludes. If it excludes more than 10% of them, stop and ask the owner before going on.
- [ ] **Report** in this ticket's comments, measured on the local copy of the production Catalog (already loaded, 38,287 Songs), before and after the tag fixes: recall@24 and precision@16 per file for version 1 (plain e5), version 17 and a version trained after the fixes, plus the first 16 Matches of the 3 owner queries above for each. End with which version to promote and why.
- [ ] README: the retag job and the order after it: `retag` → `build-vectors` → `evaluate` → `train`.

Not in scope: a larger embedding model, fine-tuning e5, new data sources, the production rollout.

**Production rollout (main session, not Bob):** after the merge deploys, run retag → build-vectors → evaluate → train on the VPS, promote the version the report recommends, and check the 3 owner queries and the Benchmark numbers in production.
