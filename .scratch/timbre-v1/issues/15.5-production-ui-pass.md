## Bugfix: search follows what the Description means

Found by the owner on 2026-11-17: searching "rock" returns A$AP Rocky first, then Travis Scott and Frank Ocean (hip hop). Cause: the name step added in ticket 14.5 (`named` in `SEARCH_SQL`, `back/src/timbre_back/main.py`) compares the Description with each single word of an artist's name (`strict_word_similarity ≥ 0.55`). "rock" scores 0.57 against "Rocky". Once anything is named, the rest of the results are ranked only by similarity to the named Songs, and the Description's own vector is dropped. "love" has the same problem through the titles "Love" (Air, Lana Del Rey) and the featured artist "Drew Love". The promoted model also scores low on the Benchmark (baseline 0.112, own v17 0.125), and it is weakest on one-word genre or mood Descriptions, even though every Song has genre tags (`catalog.songs.tags`).

- [ ] **Name matches cover the whole name.** An artist matches only when the Description matches the artist's whole name (the main artist; guests after "feat."/"ft." don't count), not a single word of it. "rock" no longer matches "A$AP Rocky", and "Linkin Park", "linkin park" and "Lana Del Rey" still do. Keep ticket 14.5's other behaviour: accent-insensitive, small typos tolerated. A title matches only as a whole title, as today, but a one-word title alone (for example "Love") must not take over a Description that also reads as a mood or genre. Choose the smallest rule that meets these examples, and record it in a one-line comment.
- [ ] **The Description's meaning is never dropped.** Named Songs still come first. The related Songs after them are ranked using the Description's own meaning too (for example by blending its vector with the named Songs' average, or by fusing the two rankings), not only by similarity to the named Songs.
- [ ] **Hybrid ranking: tags plus model.** Also score Songs by a direct match between the Description's words and each Song's tags (genres, moods), and merge that with the model's ranking, for example with Reciprocal Rank Fusion. Use Postgres features already available (full-text search or `pg_trgm`), with no new dependency. Any schema change is a dbmate migration in `back/migrations/` with bound parameters only. "rock" must return rock Songs, "rap" rap, and "jazz" jazz. Multi-word Descriptions ("guitarra suja e voz rouca, clima de estrada à noite") must not get worse.
- [ ] **The Benchmark sees these cases.** Add short genre and mood Descriptions and name clashes to the Benchmark, each with expected Songs taken from the Catalog's tags: at least "rock", "rap", "jazz", "love", "samba" or "mpb" if the Catalog has them, and one real artist search. The Benchmark must run through the same search the API uses, including the name step and the tag ranking. If it doesn't today, make it. Report the score before and after for the promoted model; the change must not lower it.
- [ ] Back-end tests cover the cases above ("rock" ≠ A$AP Rocky, an artist search still works, "love" keeps its meaning, a tag match ranks). Run ruff, mypy, pyright and pytest in Compose. If the API models change, regenerate `back/openapi.json` and `front/lib/api/schema.d.ts`.
